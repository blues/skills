## Choose the evidence

| Surface | What one object represents | What it does not establish |
|---|---|---|
| Event APIs / event datasets | A note operation or platform-generated occurrence, with body, payload and metadata | One sensor sample per row, current device state, or successful delivery to every route |
| Session APIs / full session datasets | A communication session and its usage period, updated as more information arrives | A customer's machine operating cycle, one modem power cycle, or every failed connection attempt |
| Device API | Latest known device identity, activity, firmware, location and selected diagnostics | Historical values at an arbitrary past time, or a live measurement taken when the API was called |
| Notes / Notefiles APIs | Queued or synchronized note state, depending on file type | A complete Event history; consumed outbound notes need not remain in a queue |
| Project / Fleet / environment APIs | Administrative grouping and configuration | Historical membership, actual physical position, or proof the device has applied a requested change |
| DFU status/history | A target's reported firmware and requested update attempts | Success inferred solely from an upload or an inactive progress flag |
| SIM/plans and Notehub Usage APIs | Their own accounting scope and update cadence | Byte-for-byte equivalence with Event payload size or Session traffic |

An outbound `.qo` is a queue; `.qi` is inbound and `.db` synchronizes named notes.
System-generated Event files can use `.qo` names without having been sent as a device
queue. In particular `_session.qo` is generated by Notehub. Do not infer the producer
from the suffix alone.

## Event envelope

The fields below are top-level unless prefixed with `body.`. Conditional fields may
be absent. REST serializers, routed Events and repository datasets can expose different
subsets; inspect the response, including any route transform or column mapping.

| Fields | Meaning and interpretation |
|---|---|
| `event` | Event identity. Deduplicate history by project and EventUID, not by body or coordinates. |
| `app`, `product`, `device` | ProjectUID, ProductUID and DeviceUID. `app:` identifies the project; ProductUID is not a project display name. Use DeviceUID for joins. |
| `sn`, `best_id` | Device serial and a display identifier preferring serial over DeviceUID. Neither guarantees a unique join key; serials can change or collide. |
| `sensor` | An associated sensor identity, when supplied. Different from `body.sensor` in tracking, which can name a sensor type. |
| `file`, `note` | Notefile and note identity. A database note can produce multiple update Events; Event count is not distinct-note count. |
| `req`, `updates`, `deleted` | Operation, note update count and deletion indication. `note.add`, `note.update`, `note.delete` and platform operations have different meanings. A deleted Event is not a new reading. |
| `body`, `payload`, `details` | JSON note data, optional binary data (base64 in JSON), and optional additional details. A body need not be customer-defined: native system files have their own schemas. Details are producer-specific, not a universal sensor schema. |
| `payload_length` | Size indicator when payload bytes were removed for storage reasons. Not an independent transfer-usage counter. |
| `when`, `when_ms`, `received` | Capture/event time, optional millisecond time information, and arrival at Notehub. See the time rules below. |
| `session`, `session_began`, `tls`, `continuous`, `transport` | Communication context. `session` joins a Session object. TLS/continuous describe the connection; transport can identify hub-generated events and noncellular sources. None describes the machine's duty cycle. |
| `platform` | Administrative/platform classification, not a guarantee that the row is irrelevant to the product. Health and connectivity questions often need these rows. |
| `batch_received`, `batch_number`, `batch_total` | Context for decoding an uploaded batch. Capture times within one batch can span an offline interval. Do not count the batch fields as additional readings. |
| `bulk`, `queued`, `status` | Internal/route-facing processing fields on some surfaces. Externalization can remove them. Route status is not device health and absence does not prove successful delivery. Consult route execution data for delivery questions. |
| `environment`, `fleets` | Routed environment context and associated fleet identifiers when included. Environment metadata concerns routed variables (the `$` convention), not the full effective device configuration. Do not substitute today's fleets/environment for historical Event context silently. |
| `err` | An error associated with the operation or processing. Read its scope; a lookup failure need not mean the device failed. |
| `firmware_host`, `firmware_notecard` | Last-known reported firmware strings attached when available. Not proof of an update at Event capture time. See firmware. |
| `best_*`, `where_*`, `tower_*`, `tri_*`, `triangulate` | Location families and lookup inputs. See location; they carry separate timestamps and provenance. |
| `sku`, `ordering_code`, `firmware` | Hardware identification and a numeric firmware identifier when supplied, typically in session context. Do not treat numeric firmware as a semantic-version string. |
| `rssi`, `sinr`, `rsrp`, `rsrq`, `bars`, `rat`, `bearer`, `cellid`, `bssid`, `ssid`, `iccid`, `apn` | Connection snapshot, principally on session-begin Events; also available on some other platform Events. Definitions are in sessions. They are not automatically measured for every application note. |
| `voltage`, `temp`, `moved`, `orientation`, `power_charging`, `power_usb`, `power_primary`, `power_mah` | Device/session snapshot. `moved` is a timestamp, not a count. See sessions and power. Distinguish these from similarly named body fields. |
| `hub_*`, `card_*` | Session usage reports with different provenance and timing; see sessions. Do not sum both for the same session. |

### Time, absence and precision

- `when` is Unix seconds associated with the captured note or generated Event;
  `received` is Unix seconds and can include a fractional part. Offline capture makes
  these differ legitimately. When supplied,
  `when_ms` is the full Unix epoch timestamp in milliseconds and takes precedence
  for precision; `when` is its whole-second counterpart. Do not add the two.
- GPS fix time is `where_when`; selected-location time is `best_location_when`.
  Neither is necessarily the sensor measurement time. Other location families have
  their own `*_when`. A tracking body's `time` is another explicit field, not arrival.
- Device location `when`, `last_activity` and many DFU API times use RFC3339 strings;
  Session times and raw `dfu.card.began/updated` use Unix seconds. Normalize explicitly.
- Date filters can select capture or upload time. For readings, use capture time;
  for delivery delay, compare both. Test device-clock plausibility and late arrivals.
- Many native fields omit zero values. Compact templates can also materialize an
  unmeasured field as `0`, `false` or an empty string. A schema alone cannot recover
  presence before encoding. Preserve nullability in analysis, and qualify unresolvable
  zero-versus-unavailable cases rather than using `COALESCE(..., 0)` indiscriminately.
- Numeric template encoding can round values. More decimal digits in JSON are not
  evidence of that much measurement accuracy. Latitude or longitude equal to zero
  individually is valid; do not drop every point on the equator or prime meridian.

## Device fields

| Fields | Meaning |
|---|---|
| `uid`, `serial_number`, `best_id`, `product_uid`, `fleet_uids` | Current device identity and memberships. API names differ from Event `device`, `sn`, `product`, `fleets`. |
| `provisioned`, `last_activity` | Provisioning time and last known service communication activity. Recent communication does not prove recent customer sensor data; old activity does not by itself prove power loss. |
| `sku`, `disabled`, `tags`, `contact` | Hardware SKU, administrative disable state, configured tags and contact metadata. `disabled` is not a detected hardware fault. Tags and contacts are not measurements. |
| `voltage`, `temperature` | Last reported supply volts and device temperature in degrees Celsius. These are snapshots; temperature may be internal rather than ambient. |
| `gps_location`, `tower_location`, `triangulated_location`, `best_location`, `tower_info` | Current cached locations and serving-cell identity. See location. |
| `firmware_notecard`, `firmware_host`, `dfu` | Reported versions and reported update state, not simply desired firmware. See firmware. |
| `cellular_usage[]` | Per-SIM accounting: `iccid`, current-plan bytes `used` and `limit`, `lifetime_used` bytes and `last_updated` Unix time. Check freshness; plan renewal changes the accounting window. |
| `sensors[]` | Associated `sensor_uid` and `last_activity_date` for that sensor, when supported. These are not additional Notecards. |
| `recent_when`, `recent_event_count[]`, `recent_session_count[]`, `recent_session_seconds[]` | Optional daily activity summary, anchored at the response time; index 0 is today, 1 yesterday, and so on, in the service's UTC day buckets. A partial current day is not comparable to a full prior day. Do not assume a fixed array length or use this as unrestricted history. |
| `health_log[]` | A bounded recent cache, optionally included. It can differ from the health-log endpoint's filtering and is not the full `_health.qo` history. See health. |

## Project, Fleet and configuration semantics

Project identity (`uid`/ProjectUID in its endpoint), display name and permitted ProductUIDs
serve different purposes. A ProductUID routes/provisions a product's devices into a
project; a human product description in firmware metadata is a different value.
A Fleet is a grouping/configuration scope and devices may belong to several. Membership
can be assigned or rule-driven; it is not proof of a physical installation or location.
Use the project's product knowledge for those meanings.

Environment responses distinguish variables set at that scope, defaults and effective
values. For example, device responses expose `environment_variables`,
`environment_variables_env_default` and `environment_variables_effective`. Resolve
inheritance with the effective response instead of inventing a merge order. Service-side
desired configuration and the state last reported by the device can disagree until
sync/application. Routes describe downstream processing; route enablement is not
evidence that a particular Event reached its destination.

For API families not defined here (billing, permissions, route-specific bodies,
webhooks and other administrative resources), fetch the exact operation's current
[API documentation](https://dev.blues.io/api-reference/notehub-api/) and response schema.
If a unit, enum, default or temporal meaning remains undocumented, say which claim
cannot yet be made. Do not manufacture a universal field dictionary from terse types.
